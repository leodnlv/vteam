## What vteam is

vteam is a Go CLI that orchestrates AI agents powered by `claude -p` (Claude Code's headless mode). The user defines agent prompts, triages findings, and reviews pull requests. vteam handles everything else: scheduling agent runs, managing task lifecycle, isolating work in git worktrees, and creating branches and pull requests.

**Core separation of concerns:** the Go orchestrator owns all state (files, git, aven tasks, PRs). Claude owns all intelligence (reading code, finding issues, implementing fixes). If Claude crashes mid-run, no state is corrupted — the orchestrator applies state transitions only after Claude finishes and returns structured output.

## Prerequisites

- **vteam** binary on PATH — `go install github.com/leodnlv/vteam/cmd/vteam@latest` (Go 1.27+)
- **Claude Code** CLI — `claude` must be on PATH
- **Git** — the project must be a git repository
- **aven** — local-first SQLite task manager CLI; `aven` must be installed and on PATH. All vteam tasks live in aven.
- **`gh`** (GitHub CLI) or **`glab`** (GitLab CLI) — for automatic PR creation. Without it, branches are pushed but PRs must be created manually.

## CLI commands

```
vteam                                   # interactive TUI: Overview (status), Agents (live run logs, p/n through runs; space for actions: run once, run on cron, stop cron), Info (config + agent settings); ? for keys
vteam init                              # scaffold vteam/ directory in the current project
vteam run <agent>                       # run a specific agent
vteam run <agent> --focus "..."         # run with priority context injected into the prompt
vteam run                               # (no agent) list available agents
vteam status                            # running agents (pid, task, worktree), scheduler state + next fires, each task agent's next pick, PRs awaiting merge, tasks/worktrees needing attention
vteam clean                             # remove worktrees no running agent uses, break stale locks, release orphaned active tasks
vteam ensure-merge                      # record merged PRs, cancel closed ones, reopen done tasks whose PR is labelled or conflicting
vteam cron enable <agent> [expr]        # enable an agent's cron (or merge-ensurer's); expr defaults to the agent.json cron
vteam cron disable <agent>              # disable it
vteam cron start                        # start the long-lived scheduler for the enabled crons (foreground)
vteam cron status                       # show whether the scheduler runs, the enabled crons, and next fire times
vteam skill install                     # symlink skills from skills/ into ~/.claude/skills/
vteam skill uninstall                   # remove skill symlinks from ~/.claude/skills/
```

## Project structure after `vteam init`

```
vteam/
├── vteam.config.json               # Project-level configuration
├── agent.schema.json               # JSON Schema for agent.json (generated by vteam init)
├── agents/
│   ├── improver/
│   │   ├── agent.json              # Optional: agent config (missing = all defaults)
│   │   ├── AGENT.md                # Required: system prompt only; marks the agent's existence
│   │   ├── MEMORY.md               # Optional: memory curation prompt; its existence enables memory
│   │   └── ON_FINISH.md            # Optional: post-run hook prompt; its existence enables the hook
│   ├── security-analyst/
│   ├── coder/
│   └── test-writer/
```

`vteam init` writes `agent.json`, `AGENT.md` and `MEMORY.md` for each default agent (no `ON_FINISH.md`).

`vteam init` sets `tasks.project` to the current directory name and gitignores `.vteam-worktrees/` plus `vteam/.locks/`, `vteam/.logs/`, `vteam/.runs/`, `vteam/.memory/`. Tasks live in aven, not in the repo — the real shared artifacts are the PRs.

## Configuration

### vteam.config.json

```json
{
  "baseBranch": "main",
  "platform": "github",
  "worktreeDir": ".vteam-worktrees",
  "tasks": {
    "maxRetries": 3,
    "project": "my-app",
    "label": "vteam",
    "workspace": "optional"
  },
  "mergeEnsurer": {
    "cron": "*/15 * * * *",
    "label": "vteam:changes-requested"
  }
}
```

| Field              | Description                                                                             |
| ------------------ | --------------------------------------------------------------------------------------- |
| `baseBranch`       | Branch to create worktrees from and target PRs against                                  |
| `platform`         | `"github"` or `"gitlab"` — determines which CLI (`gh` / `glab`) is used for PR creation |
| `worktreeDir`      | Where worktrees are created (relative to repo root). Gitignored.                        |
| `tasks.maxRetries` | How many times the coder retries a failing task before skipping it                      |
| `tasks.project`    | Required, non-empty. aven project for vteam's tasks; aven auto-creates it on the first task |
| `tasks.label`      | Default `"vteam"`. Opt-in label — vteam only sees/picks up tasks carrying it. Auto-created. vteam also adds `<label>-<agent>` labels: the creating agent's on new tasks (`vteam-improver`), the finishing agent's on `done` (`vteam-coder`) |
| `tasks.workspace`  | Optional. aven workspace, passed as `--workspace` to every `aven` call                  |
| `mergeEnsurer.cron` | Optional. Default cron pattern for `vteam ensure-merge` once its cron is enabled     |
| `mergeEnsurer.label` | Default `"vteam:changes-requested"`. PR label a human adds to approve review feedback; the ensurer reopens the task and removes it |

## Agent configuration (agent.json)

Agents are defined by a directory `vteam/agents/<name>/` containing `AGENT.md`. All markdown files are pure prompts: `AGENT.md` is the agent's system prompt. Orchestrator behavior lives in `agent.json` next to it (optional; missing = all defaults). Add custom agents by creating a new directory with an `AGENT.md` — no config changes needed.

### agent.json fields

All fields are optional.

```jsonc
{
  "$schema": "../../agent.schema.json",      // editor autocomplete/validation
  "model": "sonnet",                         // alias ("sonnet", "opus", "haiku") or full model ID; omit for Claude Code's default
  "cron": "0 */6 * * *",                     // default cron pattern (5 fields, no L or #); does not schedule until enabled
  "worktree": true,                          // run in an isolated git worktree
  "readOnly": true,                          // worktree but no commit/push/PR (requires worktree: true)
  "input": "task",                           // "task" (pick from the aven todo queue) or "pr" (respond to PR reviews)
  "output": "task",                          // "task" to produce findings as aven tasks
  "taskFilter": {                            // requires input: "task" — aven metadata key → value | [values] | null (missing); keys AND, list values OR
    "found-by": ["improver", "security-analyst"]
  },
  "autoPR": true,                            // create a PR after pushing
  "prTriggerLabel": "vteam:changes-requested", // label to discover PRs needing work
  "prCreateLabels": ["vteam"],               // labels applied to created PRs
  "resolveThreads": true,                    // PR follow-ups: resolve threads the agent replied to (requires input: "task" + worktree)
  "allowedTools": ["Read", "Grep"],          // Claude Code tools the agent may use; when set, also its whole built-in toolset (--tools)
  "disallowedTools": [],                     // Claude Code tools the agent may NOT use
  "memory": { "model": "haiku" },            // curation agent: model, allowedTools, disallowedTools (requires MEMORY.md)
  "onFinish": { "model": "haiku", "allowedTools": ["mcp__slack__send_message"] } // hook: same keys (requires ON_FINISH.md)
}
```

This lists every field, not a valid combination. The comments are illustrative — `agent.json` is plain JSON and must not contain them.

### Validation rules (enforced by the orchestrator)

- Strict keys: unknown keys are rejected anywhere, including inside `memory` / `onFinish`. `$schema` is allowed.
- Invalid JSON → `Invalid JSON in <name>/agent.json`; schema errors → `Invalid config in <name>/agent.json:` with one line per offending path.
- A `memory` / `onFinish` section without the matching `MEMORY.md` / `ON_FINISH.md` is a load error. The `.md` file turns the feature on; the section only configures it.
- YAML frontmatter is rejected: an `AGENT.md`, `MEMORY.md` or `ON_FINISH.md` starting with `---` is a load error telling the user to move its fields into `agent.json`. There is no migration command — old-format agents are converted by hand.
- The cross-field rules below are checked only by vteam at load time, not by `agent.schema.json`:

- `input: "pr"` requires `worktree: true`
- `readOnly: true` requires `worktree: true`
- `readOnly: true` is incompatible with `autoPR: true`
- `resolveThreads: true` requires `input: "task"` and `worktree: true`
- `output: "task"` is incompatible with `autoPR: true`
- `output: "task"` is incompatible with `readOnly: true`
- `taskFilter` requires `input: "task"`

### Common agent archetypes

| Archetype                | worktree | input  | output | autoPR | Description                                                   |
| ------------------------ | -------- | ------ | ------ | ------ | ------------------------------------------------------------- |
| Scanner / improver       | —        | —      | `task` | —      | Scans codebase, returns findings as tasks                     |
| Implementer / coder      | `true`   | `task` | —      | `true` | Picks a task, fixes it, creates a PR                          |
| PR responder             | `true`   | `pr`   | —      | —      | Responds to review comments on PRs                            |
| Read-only analyzer       | `true`   | —      | —      | —      | Reads code in a worktree, returns text (set `readOnly: true`) |
| Generic reporter         | —        | —      | —      | —      | Returns freeform text output                                  |

## How agents run

Each agent is invoked as a `claude -p` subprocess. The orchestrator assembles a layered prompt:

1. **System prompt** — the AGENT.md content
2. **Priority focus** — optional `--focus` text, injected first so Claude prioritizes it
3. **Agent memory** — accumulated memory from previous runs (if MEMORY.md exists)
4. **Existing tasks** — every non-deleted labelled task in the aven project, all statuses, as `- [status] severity | title` (for deduplication)
5. **Task content** — if `input: "task"`, the specific task to implement, followed by a `## Task Notes` section with the task's aven notes (oldest first) when it has any
6. **PR review comments** — if `input: "pr"`, the unresolved review threads
7. **Output format instructions** — JSON schema the agent must return

Claude returns structured JSON matching the unified `AgentOutput` schema:

```json
{
  "status": "completed|partial|blocked|failed",
  "summary": "what you did",
  "content": { "type": "task|generic", "body": "..." },
  "filesChanged": ["path/to/file.ts"],
  "commitMessage": { "subject": "vteam: ...", "body": "..." },
  "blockerReason": "only if blocked/failed",
  "memoryUpdate": "optional notes for future runs",
  "threadReplies": [{ "thread": "T1", "body": "what changed" }]
}
```

`threadReplies` is only requested on PR follow-ups with open review threads (labelled `T1`, `T2`, … in the prompt). Claude replies only to threads it addressed.

The orchestrator then:

- Creates an aven task from `content` when `type: "task"`
- Commits + pushes from `commitMessage` when the agent modified files
- Creates a PR if `autoPR: true`
- Sets the task to `done` (metadata `completed`, `branch`, `pr-url`) if a commit was pushed
- When an agent without a task opens a PR, creates a `done` task recording it (title from the commit subject, severity `low`, `found-by=<agent>`, metadata `completed`, `branch`, `pr-url`, plus a run note) so the merge ensurer tracks every vteam PR. Failure to record it is logged, not fatal
- Follows up on an existing PR when a worktree agent picks a task that already has `pr-url` metadata: checks out the PR branch, adds the PR's unresolved review threads to the prompt (`## Existing Pull Request`), pushes to that branch and skips `autoPR`. If the PR conflicts with its base, merges `origin/<base>` into the worktree first and lists the conflicted files in a `## Merge Conflicts` prompt section; leftover conflict markers block the commit (counted as no changes), and a clean merge is pushed even without other changes. After the push it posts the agent's `threadReplies` to their threads (`🤖 **vteam <agent>:** …` + `Fixed in <sha>`) and resolves them if `resolveThreads: true`; reply failures are non-fatal. If the PR is merged or closed, moves the task to `backlog` with a note instead of running
- Returns the task to `todo` and increments `retry-count` metadata if the agent produced no changes
- Returns the task to `todo` without incrementing on any other ending (crash, error, readOnly or non-worktree agent)
- Appends an aven note to the task (`<agent>: <status>`, `summary`, `Blocker: …`, `PR: …`) whenever the agent returned output; a failed note write is non-fatal
- Passes `content` through to the ON_FINISH hook

## Task lifecycle

```
improver finds issue → aven task in inbox
human triages → todo
coder picks task → active → implements fix → branch + PR → done
no changes / crash / error → active → back to todo
review comments to apply → human adds the vteam:changes-requested PR label → vteam ensure-merge moves the task to todo → coder pushes to the same PR → done
PR conflicts with base → vteam ensure-merge moves the task to todo → coder merges base, resolves conflicts → done
PR merged → vteam ensure-merge sets merged=true; PR closed → task canceled
```

Tasks live in aven, scoped to `tasks.project` + `tasks.label`. Refs look like `APP-7KQ9` (recorded as `taskRef` in `vteam/.runs/*.json`).

- **Creating** (`output: "task"`): `aven add` with `--project`, `--status inbox`, `--label`, priority from severity (critical→urgent, high→high, medium→medium, low→low), metadata `found-by=<agent>`, and a markdown description (Description / Suggested Fix / Affected Files). Aven priority `none` reads back as `low`. aven promotes inbox tasks with priority medium or higher to `todo` on add, so vteam follows up with `aven edit <ref> --status inbox`. Tasks are only picked once a human moves them to `todo`.
- **Routing**: each `input: "task"` agent's `taskFilter` (in `agent.json`) selects tasks by aven metadata — keys AND, list values OR, `null` = key missing/empty. No `taskFilter` = matches everything. There is no fallback: a task no agent's filter matches is never picked (`vteam status` warns and shows each agent's next pick). Overlaps are allowed; picking runs under a global claim lock, so exactly one agent gets each task. vteam only writes `found-by`; other keys (e.g. `actor`) are set by humans via `aven edit <ref> --metadata actor=<agent>`.
- **Picking** (`input: "task"`): `aven list --project P --label L --status todo --ready` (one `aven show` per ready task), then routed in-process as above, so aven dependency blocking and `available_at` deferral are respected. Tasks with `retry-count` >= `maxRetries` are skipped. Sorted by severity (`critical` > `high` > `medium` > `low`), then oldest first. The picked task is set to `active` immediately with metadata `claimed-by` (runId), `claimed-pid`, `claimed-host`. The whole list → pick → `active` step holds `vteam/.locks/task-claim` (shared by all agents, released before Claude runs), so concurrent agents with overlapping filters never get the same task. Claim metadata is removed whenever the task leaves `active`. Local to one machine only.
- **Branch names**: `vteam/<slugified-title>-<runId>` — aven refs are local and are kept out of remote systems.
- **Human triage**: users can manage tasks in aven (`aven tui` or CLI) — move findings to backlog/canceled, reprioritize, add dependencies, or add the `vteam` label to their own tasks to queue them for the coder. Canceled tasks still appear in the dedup list, so canceling marks a finding as rejected/false positive.
- **Merge ensurer** (`vteam ensure-merge`, no Claude): for each `done` task with `pr-url` and without `merged=true`, looks the PR up. Merged → metadata `merged=true`. Closed → `canceled` + note. Open with `mergeEnsurer.label` → removes the label first (if that fails the task stays done), then `todo`, clears `retry-count`, adds a note. Open and conflicting → `todo` + note. Otherwise nothing; comments alone never reopen a task. Unknown mergeability is skipped. Holds `vteam/.locks/merge-ensurer`, logs to `vteam/.logs/merge-ensurer/`.
- **PR follow-ups**: add the `mergeEnsurer.label` to the PR, or reopen by hand with `aven edit <ref> --status todo` plus `aven note <ref> "<which comments to apply>"`. The task's `pr-url` makes the run check out the PR branch and see its unresolved review threads. A merged or closed PR parks the task in `backlog`; remove `pr-url` (`aven edit <ref> --remove-metadata pr-url`) to start over on a new branch.
- **Hard kill**: if the vteam process is killed, the task may remain `active`. `vteam clean` returns it to `todo` when `claimed-host` is this machine and `claimed-pid` is dead; otherwise reset it with `aven edit <ref> --status todo`.

## Optional agent files

### MEMORY.md — persistent memory across runs

Place alongside AGENT.md; its content is the curation agent's system prompt and its existence enables memory. The curation agent's `model` / `allowedTools` / `disallowedTools` go in the `memory` section of `agent.json`. The orchestrator:

1. Injects accumulated memory into the agent's prompt before each run
2. Extracts `memoryUpdate` from the agent's output
3. Spawns a curation agent that merges new updates into existing memory per the MEMORY.md rules
4. Writes the curated result to `vteam/.memory/<agent-name>/store.md`

```markdown
Keep a running list of areas scanned. Record false positives.
Maximum 30 lines — drop oldest entries first.
```

```json
{ "memory": { "model": "haiku" } }
```

### ON_FINISH.md — post-run hooks

Place alongside AGENT.md; its content is the hook's system prompt and its existence enables the hook. The hook's `model` / `allowedTools` / `disallowedTools` go in the `onFinish` section of `agent.json`. After the agent finishes (success or failure), the orchestrator spawns a second `claude -p` call with the run outcome. Use for notifications, logging, or follow-up actions.

```markdown
Post the run result to the #eng-prs Slack channel.
```

```json
{ "onFinish": { "model": "haiku", "allowedTools": ["Bash(curl *)", "mcp__slack__send_message"] } }
```

The hook receives: agent name, status, timestamps, task details, branch, PR URL, content output, and error (if any). It runs in the main project directory. Hook failure does not affect the agent run's exit status.

## Worktrees

Agents with `worktree: true` get an isolated git worktree, branched from a freshly fetched `origin/<baseBranch>`. Claude edits files there but does NOT commit — it returns a commit message in its JSON output. The orchestrator runs `git add -A` + `git commit`, pushes the branch, and optionally creates a PR. Worktrees are cleaned up after each run. Pushes use `--force-with-lease` against the remote sha at worktree creation (new branch: must not exist; PR branch: the checked-out sha), so a human's concurrent pushes are never overwritten. Network errors are retried twice.

## Locking

Advisory file locking via atomic `mkdir`. Each lock contains PID + timestamp. A lock is stale only when its holding process is dead (or it has no info file and is older than 30 minutes); a live run keeps its lock however long it takes. Same-agent runs are serialized; different agents can run concurrently. Task picking is serialized across all agents by the `task-claim` lock. `vteam clean` breaks only stale locks.

## Scheduling

Crons are opt-in per agent. The `cron` in `agent.json` (and `mergeEnsurer.cron` for the job `merge-ensurer`) is only a default pattern. A cron runs once it is enabled, either in the TUI (Agents tab: `space` → "Run on cron…", or `c`) or with `vteam cron enable <agent> [expr]`. Enabled crons are local state in `vteam/.cron/schedules.json` (gitignored by its own `.gitignore`). `vteam cron start` (foreground, Ctrl+C to stop) runs them. It rereads that file every 2s, so enable/disable/change take effect live, and it exits by itself once no cron is enabled and nothing it started is running. The TUI starts the scheduler in the background (output in `vteam/.cron/scheduler.log`) when you enable a cron and none is running. Enabled crons with no scheduler show as paused; `S` in the TUI or `vteam cron start` resumes them. Cron expressions have 5 fields with ranges, steps, lists, and month/weekday names; `L` and `#` are rejected, and when both day-of-month and day-of-week are set either one matching fires. If an agent is still running when its next tick fires, the tick is skipped. The scheduler writes its pid to `vteam/.locks/cron.pid`, refuses to start twice, and `vteam status` reads that file to report whether it is running.

Every `vteam run <agent>`, whether started by hand or by the scheduler, writes its full output to `vteam/.logs/<agent>/<ISO-timestamp>.log` and still prints to the terminal. Check there first when troubleshooting a run. The output is split into sections (Setup, Agent, Result, hooks, Cleanup) with an elapsed-time gutter. Glyphs: `•` step, `❯` Claude text, `⚙` tool call, `✗` failed tool or error, `!` warning. The file has no colors and keeps full tool inputs.

## The `--focus` option

All `vteam run` invocations accept `--focus <text>` to inject priority context. The text appears as the first section of the user prompt.

```bash
vteam run improver --focus "only look at the auth module"
vteam run coder --focus "the issue about XYZ"
```

## Default agents

| Agent                | Purpose                           | Key traits                                      |
| -------------------- | --------------------------------- | ----------------------------------------------- |
| **improver**         | Scans codebase for issues         | Read-only, `output: task`, no worktree, `cron: "0 * * * *"` |
| **security-analyst** | Scans for one security finding per run (dependencies, injection, data leaks, missing mechanisms) | Read-only plus `npm/pnpm/yarn audit`/`outdated`, `output: task`, no worktree, `cron: "15 */4 * * *"` |
| **coder**            | Picks a task and implements a fix | `input: task`, `worktree: true`, `autoPR: true`, `taskFilter: { "found-by": ["improver", "security-analyst", "test-writer", null] }`, `cron: "*/5 * * * *"` |
| **test-writer**      | Adds tests for untested code; each PR is recorded as a `done` task | `worktree: true`, `autoPR: true`, `cron: "30 */2 * * *"` |

## Creating a custom agent

1. Create `vteam/agents/<name>/AGENT.md` with the system prompt (no frontmatter)
2. Add `vteam/agents/<name>/agent.json` with `"$schema": "../../agent.schema.json"` and any config fields (omit for all defaults)
3. Optionally add `MEMORY.md` and/or `ON_FINISH.md` alongside it, configured via the `memory` / `onFinish` sections of `agent.json`
4. Run with `vteam run <name>`

No config changes needed — the orchestrator discovers agents by scanning the `vteam/agents/` directory.

## Tool permission patterns

`allowedTools` does two things: it pre-approves the listed tools (`--allowedTools`) and, when set, removes every other built-in tool (`--tools`, built from the names: `Bash(npm *)` → `Bash`). MCP tools (`mcp__*`) are not built-in, so they only need listing to be pre-approved; MCP servers from the user's Claude Code config stay available. A hook with `["mcp__slack__send_message"]` gets no built-in tools at all.

Agent runs also get `--json-schema` with the `AgentOutput` schema for that agent, so the final answer is validated by Claude Code and read from `structured_output`.

Common `allowedTools` presets:

- **Read-only**: `["Read", "Glob", "Grep"]`
- **Read-write**: `["Read", "Edit", "Write", "Glob", "Grep", "Bash(npm *)", "Bash(npx *)", "Bash(cat *)", "Bash(ls *)"]`
- **Read-write + git platform**: above plus `"Bash(gh *)"` and/or `"Bash(glab *)"`

## Key design principles

1. **Orchestrator owns state, Claude owns intelligence** — strict separation. Claude never creates tasks, commits, or pushes. The orchestrator never reasons about code.
2. **Stateless agents** — every `claude -p` call starts fresh. All context is injected via the prompt (task content, memory, existing task titles).
3. **Atomic state transitions** — if Claude crashes, no state is corrupted. The orchestrator applies changes only after Claude finishes.
4. **Local-only workflow state** — tasks live in local aven; locks, logs, run state, and memory are gitignored. The shared artifacts are PRs and branches.
5. **Title-based deduplication** — the orchestrator injects all existing task titles into every agent's prompt so Claude avoids reporting duplicates.
6. **Minimal dependencies** — Slug generation and utilities are internal modules with no external dependencies.

## Troubleshooting

- **Stuck lock**: If the holding process is dead, the next run or `vteam clean` breaks it. If it is alive, the run is still going — kill it first.
- **Orphaned worktree**: `vteam status` lists worktrees no running agent uses. Run `vteam clean` to remove them; it keeps worktrees a running agent is using.
- **Agent produced no changes**: Check the task's `retry-count` metadata (`aven show <ref>`). After `maxRetries` failures, the task is skipped.
- **PR creation failed**: Verify `gh` or `glab` is installed and authenticated. The branch is still pushed — create the PR manually.
- **No eligible tasks**: Run the improver first, then move its findings from `inbox` to `todo` (`aven edit <ref> --status todo`), or add the `vteam` label to existing aven tasks in the project. Tasks blocked by dependencies or deferred are not ready.
- **Task stuck in `active`**: The vteam process was killed mid-run. Run `vteam clean` on the machine that claimed it, or reset with `aven edit <ref> --status todo`.
- **`... starts with YAML frontmatter, which is no longer supported`**: Old-format agent. Move the frontmatter fields into `agent.json` (memory/hook fields into `memory` / `onFinish`) and leave only the prompt in the `.md` file.
- **`aven CLI not found on PATH`**: Install aven and make sure `aven` is on PATH.
